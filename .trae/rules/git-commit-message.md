# Trae Git 提交内容生成规则

本文件供 Trae 在为本仓库生成 Git 提交信息时读取。请根据实际 Git 变更生成提交内容，不要编造 diff 中不存在的功能、修复或影响范围。

## 读取顺序

1. 优先分析 `git diff --staged`。
2. 如果暂存区没有变更，再分析 `git diff` 和 `git status --short`。
3. 如果没有检测到任何变更，返回：`无法生成提交内容：当前没有 Git 变更。`
4. 如果变更内容不完整或意图不明确，生成一个保守的提交信息，并在正文中说明依据。

## 输出格式

默认使用 Conventional Commits 风格，提交标题使用中文：

```text
<type>(<scope>): <summary>

<body>
```

当变更很小且标题已经足够清楚时，可以只输出标题，不写正文。

## type 规则

- `feat`: 新增功能、页面、交互或用户可见能力
- `fix`: 修复 bug、异常、兼容性问题或错误逻辑
- `refactor`: 重构代码，但不改变外部行为
- `perf`: 性能优化
- `style`: 样式、布局、格式、视觉调整，不影响逻辑
- `docs`: 文档变更
- `test`: 测试相关变更
- `chore`: 依赖、脚本、配置、工程维护
- `build`: 构建系统或打包配置变更
- `ci`: CI/CD 配置变更
- `revert`: 回滚提交

## scope 规则

scope 使用小写英文，优先选择最能代表改动范围的模块名：

- `map`: 地图、图层、标记点、定位相关变更
- `auth`: 登录、微信授权、权限拦截相关变更
- `api`: 接口请求、接口模块、请求参数相关变更
- `router`: 路由、菜单、页面跳转相关变更
- `store`: Pinia 状态管理相关变更
- `home`: 首页相关变更
- `layout`: 全局布局相关变更
- `styles`: 全局样式、主题、移动端适配相关变更
- `deps`: 依赖版本、锁文件相关变更
- `config`: Vite、UnoCSS、ESLint、JS 配置相关变更
- `docs`: README 或其他文档相关变更

如果改动跨多个模块且没有明显主模块，可以省略 scope：

```text
chore: 整理项目基础配置
```

## summary 规则

- 使用中文短句，建议 20 到 50 个中文字符。
- 使用动宾结构，突出“做了什么”。
- 不要以句号、逗号、感叹号结尾。
- 不要写“修改了一些文件”“更新代码”“修复问题”这类泛泛描述。
- 优先描述用户可感知的行为，其次描述技术实现。

推荐示例：

```text
feat(map): 增加地图图层切换状态
fix(auth): 修复微信授权回跳参数丢失
style(home): 优化首页移动端布局间距
chore(deps): 更新移动端构建依赖
```

不推荐示例：

```text
update code
fix bug
修改文件
优化项目
```

## body 规则

当一次提交包含多个关键点、影响范围较大或标题无法完整表达时，补充正文。正文使用 1 到 3 条中文 bullet：

```text
feat(map): 增加地图图层切换状态

- 新增图层选中状态的持久化逻辑
- 调整地图标记点渲染时机
- 影响地图首页的图层展示流程
```

正文应说明：

- 核心改动
- 影响范围
- 兼容性、风险或需要注意的地方

正文不应做这些事：

- 逐条罗列所有文件名
- 复述大量代码细节
- 夸大 diff 中没有体现的业务价值
- 添加未经确认的 issue 编号、需求编号或负责人

## footer 规则

只有在 diff 或用户输入明确出现时才添加 footer。

破坏性变更格式：

```text
BREAKING CHANGE: 说明不兼容的变更和迁移方式
```

关联 issue 格式：

```text
Closes #123
```

## 多类型变更的选择

当一次提交同时包含多类变更时，选择最主要、最有用户或系统影响的 type：

1. 修复线上或明显错误，优先 `fix`。
2. 新增能力，优先 `feat`。
3. 纯样式视觉调整，使用 `style`。
4. 仅工程配置或依赖，使用 `chore`、`build` 或 `ci`。
5. 行为不变的代码整理，使用 `refactor`。

如果变更明显可以拆成多个提交，请给出建议拆分方式，而不是强行生成一个模糊的大提交。

## 最终输出要求

- 只输出提交内容本身，除非用户要求解释。
- 不要包裹 Markdown 代码块。
- 不要输出分析过程。
- 不要生成英文标题，除非用户明确要求。
- 不要自动执行 `git commit`，除非用户明确要求。
